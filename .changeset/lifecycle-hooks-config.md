Add lifecycle hooks (Preview) and a `git.neonSafeBranchName` helper.

- New `experimental.hooks` policy field with `checkout`, `create`, and `deploy` phases, each exposing a `before` (influence/abort) and `after` (observe) hook. `experimental` is its own top-level namespace — not a sibling of `auth` / `dataApi` / `branch` — so an experimental feature can change shape or be removed without touching the policy's stable surface. A hook is a function `(ctx) => …` or a shell command (string or array). Hooks are the imperative companion to the pure `branch()` closure and are read by the runtime only on the real `checkout` / `deploy` commands (and, for `create`, only when those actually create a branch) — never during `plan` / `status` / `inspect`.
- `create` fires only when a branch is actually created — never when `checkout` selects an existing one. Unlike `checkout.before`, `create.before` cannot rename the branch (the name is already resolved by then); it can still abort.
- Every context carries a typed `event` describing what triggered it, instead of the removed `GitContext.triggeredByGitHook` boolean. `checkout` / `create` get a `CheckoutEvent`: `{ type: "git-checkout"; gitBranch: string }` (the installed git hook — `inputName` is never present on this variant) or `{ type: "neon-checkout"; inputName?: string }` (an explicit `neonctl checkout`). `deploy` gets a `DeployEvent`, currently always `{ type: "neon-deploy" }`. Narrowing on `event.type` narrows `event.gitBranch` / `event.inputName` accordingly — TypeScript only exposes the field the matched variant actually has.
- New hook context types: `ExperimentalInput<C>`, `Hooks<C>`, `CheckoutHooks<C>`, `CreateHooks<C>`, `DeployHooks<C>`, `CheckoutEvent`, `DeployEvent`, `CheckoutBeforeContext`, `CheckoutBeforeResult`, `CheckoutAfterContext<C>`, `CreateBeforeContext`, `CreateAfterContext<C>`, `DeployBeforeContext`, `DeployAfterContext<C>`, `GitContext`, `HookBranch`, `Hook`, `ShellHook`. The `after` contexts are generic over the policy so their `env` is the **exact** `NeonEnv<typeof config>` — `env.auth` / `env.dataApi` / `env.storage` / `env.aiGateway` are present iff the policy enables them (no `unknown` escape hatch).
- The canonical `NeonEnv<C>` type family now lives in this package (`NeonEnv`, `NeonPostgresEnv`, `NeonBranchEnv`, `NeonAuthEnv`, `NeonDataApiEnv`, `NeonStorageEnv`, `NeonAiGatewayEnv`, `FunctionSlugOf`, `NeonFunctionEnv`). It's a pure, runtime-free shape derived from `Config`, so config can type a `neon.ts` hook's `env` exactly without a `config` → `env` dependency cycle. `@neondatabase/env` re-exports these, so its public surface is unchanged.
- New `git` namespace (alongside `errors` / `schemas`) with `git.neonSafeBranchName` (and `NeonSafeBranchNameOptions`), which derives a valid, stable Neon branch name from an arbitrary string (e.g. a git branch) — shared with the CLI's git → Neon mapping. Pass `preserveSlashes: false` for a single flat token. Grouped rather than a bare top-level export because a hook context's own `git` field (read-only checkout facts) would otherwise shadow it — import under an alias (`git as neonGit`) at call sites that also destructure a hook context's `git`.
- `schemas.hooks` and `schemas.experimental` are added to the exported schema namespace.
